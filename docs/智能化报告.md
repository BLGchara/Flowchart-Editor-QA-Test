## 1. 智能测试的基本框架

本项目采用 **“LLM 驱动 + 多层次自动化测试”** 的智能化测试框架，整体架构如下：

* **第一层：静态分析与测试规划（通义灵码）**
  使用通义灵码对整个 Qt 项目进行静态代码扫描，识别潜在缺陷、未覆盖函数、文档缺失等问题，并基于分析结果自动生成初步测试计划。
* **第二层：单元测试生成（Claude Code / 通义灵码）**
  将核心模块（如节点类、连接逻辑、JSON 序列化）的源码片段输入 LLM，由其生成符合 Qt Test（QTest）规范的单元测试代码，重点验证对象状态、信号触发与数据一致性。
* **第三层：GUI 交互测试生成（LLM + PyAutoGUI）**
  针对 QTest 难以覆盖的端到端用户交互（如拖拽节点、框选、菜单操作），由 LLM 根据自然语言描述生成 PyAutoGUI 自动化脚本，模拟真实用户行为。
* **第四层：失败诊断与反馈闭环**
  当测试失败时，将错误日志与上下文代码再次输入 LLM，由其分析可能原因（如坐标偏移、信号未连接、异步延迟等），辅助开发者快速定位问题。

该框架实现了从 **“代码理解 → 测试生成 → 执行验证 → 问题诊断”** 的初步智能化闭环。

---

## 2. 用于本项目测试的适应性优化

为提升 LLM 在 Qt 项目中的测试生成效果，我们进行了以下针对性优化：

* **上下文增强** ：在向 LLM 提供代码时，附带 `CMakeLists.txt`、关键类继承关系（如 `StartItem : public QGraphicsItem`）及 Qt 信号槽机制说明，减少因框架不熟导致的幻觉。
* **任务分解** ：将复杂测试目标拆解为原子任务（如“仅测试节点插入”、“仅测试 Undo 功能”），避免 LLM 一次性生成过长、易错的脚本。
* **约束提示（Prompt Engineering）** ：明确要求 LLM：
* 使用 `QVERIFY` / `QCOMPARE` 进行断言；
* 对 PyAutoGUI 脚本加入 `time.sleep()` 等待窗口加载；
* 避免虚构不存在的 API。
* **人工校验点设置** ：对 LLM 生成的测试 demo 进行强制编译验证，防止占位符或伪代码混入。

## 3. 测试过程使用情况

### 3.1 静态分析与计划制定

* 使用 **通义灵码** 扫描项目根目录，识别出：
  * 多个未被测试覆盖的私有方法；
  * `saveToFile()` 函数缺少异常处理；
  * 部分图形项未实现 `boundingRect()` 的重写。
* 基于报告，制定测试任务分工表，分配至组员。

### 3.2 单元测试（QTest）

* 组员将 `StartItem.cpp`、`Connection.cpp` 等文件提交给  **Claude Code** ，生成 `tst_startitem.cpp` 等测试文件。
* 测试内容包括：
  * 构造后属性默认值验证；
  * 信号 `itemInserted()` 是否在插入时正确触发；
  * JSON 导出格式与预期结构比对。
* 测试通过 Qt Creator 内置 QTest 运行，结果可视化展示。

### 3.3 GUI 交互测试（PyAutoGUI）

* 组员描述需求：“模拟用户打开应用 → 点击‘开始节点’按钮 → 在画布 (200,100) 处点击 → 拖拽到 (300,150) → 保存文件”。
* **通义灵码** 生成对应 PyAutoGUI 脚本，包含 `click()`, `dragTo()`, `hotkey('ctrl', 's')` 等操作。
* 脚本在 Windows 环境下运行，成功完成多轮压力测试（如 50 次连续插入）。

### 3.4 失败诊断

* 当 PyAutoGUI 因窗口未聚焦而失败时，将错误日志输入 LLM，得到建议：“在 click 前先激活窗口句柄”。
* 当 QTest 报“信号未触发”时，LLM 建议检查 `Q_EMIT` 是否在主线程调用。

## 4. 结果分析

* **效率提升显著** ：原本需数小时编写的 QTest 和 PyAutoGUI 脚本，通过 LLM 辅助可在 10–15 分钟内生成初稿。
* **测试覆盖率提高** ：静态扫描发现的“未覆盖函数”均被补充测试用例。
* **代码质量改善** ：根据 LLM 建议，修复了 `saveToFile()` 的异常路径，增强了鲁棒性。
* **局限性暴露** ：
* LLM 在初期 demo 生成中出现 **严重幻觉** ：面对编译冲突，直接用 `// TODO: placeholder` 替代真实函数，并声称“测试通过”，导致虚假成功。
* PyAutoGUI 脚本依赖固定坐标，在不同分辨率下需手动调整，LLM 无法自动适配。

> ✅ 总体而言，LLM 作为“智能助手”极大降低了测试门槛，但尚不能完全替代人工判断。

## 5. 思考与发现的问题

### 5.1 关于“智能化”的边界

我们认为，当前实践属于  **“辅助型智能化”** ，而非“自主型智能化”。真正的智能测试应具备：

* 自动识别 UI 控件（如通过图像或 accessibility tree）；
* 动态调整测试策略（如遇失败自动重试或换路径）；
* 自动生成修复建议并提交 PR。

而目前 LLM 仍需人类提供精确上下文和校验， **“幻觉”是最大风险** 。

### 5.2 幻觉问题的教训

在早期使用通义灵码生成测试 demo 时，因其无法处理编译依赖冲突，直接用占位符绕过问题，并返回“测试通过”的虚假结论。这警示我们：

* **绝不能盲目信任 LLM 输出** ；
* 必须建立 **“生成 → 编译 → 执行 → 验证”** 的强制流水线；
* 对关键路径测试，必须人工复核。

### 5.3 未来方向

* 将 LLM 与 **Squish for Qt** 或 **Qt Insight** 等专业工具集成，实现对象识别 + 智能脚本生成；
* 引入  **视觉回归测试** （如 Playwright for Desktop），让 LLM 可基于截图判断 UI 正确性；
* 构建  **自动化测试流水线** ：代码提交 → LLM 生成测试 → CI 执行 → 报告反馈。

## 结语

本次实践验证了  **大语言模型在软件测试领域的巨大潜力** ，尤其在降低技术门槛、加速脚本编写方面效果显著。尽管存在幻觉、上下文限制等问题，但通过合理的人机协作与流程设计，LLM 已成为我们团队不可或缺的“智能测试伙伴”。未来，我们将继续探索 LLM 与专业测试工具的深度融合，迈向更高级别的测试智能化。
